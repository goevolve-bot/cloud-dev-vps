# B3 — Runner and queue: make runs deliver work

**You are fixing the execution path.** Today an implement run leaves the agent's
work uncommitted, pushes an unchanged branch, reports success, and triggers a
verify that sees none of it — and the next run on that task silently destroys the
work. Concurrent runs collide on IDs, the queue can double-start, and verify is
unstreamable, untimeoutable, and probably fails before it runs a single test.

This is the largest batch and touches two files heavily. Prerequisites: **B1 and
B2 committed** (B3 changes the runner protocol, which B2 also touches lightly).

This work order is self-contained. Do not read `docs/pm-implementation-review.md`.

## Issues to fix

### 3.1 — Implement runs deliver nothing (review §3.5)

`handlers.ts` (~line 705) `commitAndPush` with a branch does exactly one thing:
`git push origin <branch>` from the task worktree. **It never stages or commits.**
And `server/prompts/implement.txt` never instructs the agent to commit either — it
ends at *"You should modify the files to implement the features described in the
description and plan."*

So an implement run leaves dirty, uncommitted files in the worktree, pushes an
unchanged branch, reports success, and auto-triggers verify — which clones the repo
and sees nothing. Worse: the next non-implement run on that task resets the
worktree (`handlers.ts` ~lines 684–689), silently destroying the uncommitted work.

**Fix:**
- Add explicit commit instructions to `implement.txt` (the plan assumed "the agent
  commits in the workspace"; that instruction was simply never written).
- **And** have `commitAndPush` stage and commit any residual changes before pushing
  — belt and braces, since an agent that forgets to commit must not lose work.
  Decide what happens when there is nothing to commit (a no-op push is fine) and
  when the push is rejected.
- The worktree reset at ~684 is a data-loss hazard even after the above. Make it
  refuse to discard uncommitted changes, or commit them first.

### 3.2 — `task.branch` is never set (review §4.2)

`setTaskBranch` exists in `core` and has **zero callers**, so the front-matter
`branch` field stays `null` and the branch chip in the task header never renders —
even though the runner does create `pm/task-<id>-<slug>`. Call it when the branch
is created.

### 3.3 — Runner run IDs collide across tasks (review §3.6)

`handlers.ts` (~lines 538–541) derives the run id from the count of `runs/*.md`
files **inside one task folder**, so two different tasks both produce run `1`. That
id is then used for a global log path (`~/logs/1.log`, ~line 53) and a global
container name (`pm-agent-run-1`, ~line 598). With the global concurrency limit of
2, two concurrent runs on different tasks will interleave their logs into one file
and the second `docker run` will fail on a name conflict.

Meanwhile pm's own `runs.id` is a proper autoincrement that is **never sent to the
runner**; the mapping lives only in an in-memory `Map` (`queue.ts` ~line 62,
`activeRunnerRunIds`), so after a pm restart no in-flight run can be stopped or
streamed.

**Fix — pm owns the run id.** Add `runId` to `StartRunArgs` in
`core/src/pm/runner-protocol.ts`, have `queue.ts` pass its own row id, and use that
id for log paths and container names in the runner. Persist it on the row so
restarts can reattach. The per-task `runs/NNNN.md` numbering is a separate,
legitimate thing — keep it, but stop using it as an execution identity.

### 3.4 — The runner ignores the environment projectctl gives it (review §3.7)

`render_runner_unit` (`pm-projectctl` ~lines 918–923) exports `PM_REPO_DIR`,
`PM_CREDS_DIR` and `PM_DEPLOY_KEY`. **The runner reads none of them.** Instead
`findRepoDir()` (`handlers.ts` ~line 78) lists `~/work` and returns the first entry
not starting with `task-`. Verify workspaces are named `verify-<task>-<run>` and
live in the same directory — so while a verify is in flight, `findRepoDir()` can
return the temporary verify checkout as "the repo", and that path is then used for
`.pm/` writes and `commitAndPush`.

**Fix:** read `PM_REPO_DIR` (and the other two where relevant) and treat them as
authoritative. Keep a fallback only if you can make it unambiguous; a hard failure
when the env var is missing is preferable to picking the wrong directory.

### 3.5 — Queue races and stranded runs (review §3.8)

`queue.ts` (~line 180) fires `void this.executeRun(run)` and loops after 10 ms. When
the project's runner is not connected, `executeRun` awaits
`callProjectctl("start", …)` **before** flipping the row to `running` (~line 199 vs
~line 217), so the loop re-reads the same still-`queued` row and starts it a second
time.

Separately, `init()` only marks `running` → `interrupted`; it never calls
`trigger()`, so runs that were `queued` at shutdown sit forever until someone posts
a new run.

**Fix:** flip the row to `running` before any await, and trigger the queue on boot.

### 3.6 — Verify starts the one-shot services it is meant to run separately (review §3.9)

`handlers.ts` (~line 346) runs `docker compose up --wait --build` over the *whole*
compose file, then runs `test` and `e2e` via `compose run`. Nothing excludes the
one-shot services from the `up` (no profiles, no `--scale test=0`), so `--wait` will
also wait on containers that exit immediately — which Compose reports as a startup
failure. On the plan's own reference project shape (main service + `test` + `e2e`),
verify looks likely to fail before running a single test.

**This one needs on-host confirmation** — the code as written does not match the
contract it is enforcing, but the exact Compose behaviour should be checked against
a real sample repo on the VPS. Fix the code (explicit service list or profiles),
and flag it in your summary as needing verification.

Related, smaller verify issues, all in scope:

- It clones the **local** repo (`git clone repoDir`), not `origin`, so it does not
  verify what was actually pushed. The plan's git flow step 5 wants the pushed
  branch checked out fresh.
- The verify run is never registered in `activeRuns` (~line 546), so `stopRun`
  cannot cancel it and `streamLogs` immediately returns `complete: true` — the live
  tail for verify is dead on arrival.
- `executeVerify` is launched with `void` and has **no timeout**; a hung
  `compose up --build` blocks the run forever. The 30-minute timeout only applies to
  agent containers (~line 650).
- Teardown runs `docker compose -p <name> down -v` without `-f`, from the runner's
  cwd, with the verify directory already about to be deleted. Leftover volumes are
  plausible. Make teardown explicit and robust.

### 3.7 — Review phase doesn't match its spec (review §4.4)

The plan wants review to run against a **fresh checkout** with the **project env
started**, so the agent can poke the running app. The implementation reuses the
existing task worktree and starts nothing. Align it — you now have working verify
env machinery from §3.6 to reuse.

### 3.8 — Review diff is computed in the wrong process, without git (review §3.10)

`server/src/prompts.ts` (~lines 78–87) shells out to `git diff main...pm/task-N-slug`
with `cwd: repoDir` — **from inside the pm container**. That violates the plan's
"pm never runs git for a project", it cannot work without the repo mounted, and the
pm image is `node:22-alpine` with **no git installed at all**. The failure is
swallowed into the prompt text: every review run is handed
`Could not generate git diff: …` as its diff.

**Fix:** add a runner verb (e.g. `diff`) to `runner-protocol.ts`, implement it in
`handlers.ts`, and have `prompts.ts` call it through the runner client. Do not
install git in the pm image — the point is that pm doesn't run git for projects.

### 3.9 — Log writes are fire-and-forget (review §4.6)

`handlers.ts` (~lines 140 and 661) call `void logManager.appendLine(...)` per line
with no serialization; concurrent `appendFile` calls can interleave and the
emitter's `end` can fire before the last append lands.

This is not theoretical: `runner/src/socket-server.test.ts` ("startRun, streamLogs,
stopRun, and commitAndPush work end-to-end") **fails under load** (`pnpm -r test`)
and passes when run alone — the reviewer reproduced both. Serialize appends and
make `end` wait for the queue to drain. The flaky test should then pass reliably in
a full run.

### 3.10 — Run success is inferred only from a JSON `result` event (review §4.7)

`queue.ts` (~line 280) infers success from a JSON `result` event. The container's
exit code is never reported back by the runner, so a crashed agent that emitted no
JSON and a successful agent with a different output shape are **both** recorded as
`failed`, with `exit_code` a synthetic `0`/`1`. Report the real exit code through
the protocol and use it.

### 3.11 — No automatic status transitions (review §4.5)

The plan's flow is implement → verify → `ready for review`. In practice only a
*review* run moves a task (`queue.ts` ~line 313); nothing ever moves a task to
`in-progress`, and verify never lands it in `ready-for-review`. The board doesn't
reflect reality unless the user drives the status dropdown by hand. Wire the
transitions.

### 3.12 — Idle timeout is 30 min, plan says 15 (review §4.11)

`queue.ts` reads `PM_IDLE_TIMEOUT_MS` defaulting to `30 * 60 * 1000`. The plan says
15 minutes, configurable **per project**. Also missing: the plan's "compose down
leftover verification environments" step. Fix the default, make it per-project
configurable, and implement the leftover-teardown sweep.

Per-run timeout (hardcoded 30 min at `handlers.ts` ~650) and global concurrency
(hardcoded at `queue.ts` ~149) should likewise become configurable with those values
as defaults.

### 3.13 — Delete the committed stream-of-consciousness (review §3.6)

`handlers.ts` lines ~489–525: roughly 37 lines of the generating agent's reasoning
("Wait! Let's check…") were committed verbatim into the production `startRun`
handler. Delete them.
