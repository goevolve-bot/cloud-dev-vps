## Background you need

`pm-projectctl` is driven over a unix socket at `/srv/pm/projectctl.sock`, one
NDJSON request per line. `app.ts` already has a `callProjectctl` helper — read it
before adding callers.

**`create`** (`verb_create`, line ~979) takes `{ name, gitUrl }`. It is idempotent
and resumable, and emits progress events with stage names: `user`, `home`,
`linger`, `docker`, `key`, `clone`, `scaffold`, `runner`, `done`. It has two
terminal shapes:

- `status: "awaiting-key"` — returns `publicKey` and a message; the repo isn't
  reachable with the deploy key yet. The caller is expected to show the key, let
  the user add it to GitHub with write access, then **call create again** to
  finish from the clone step.
- `status: "ready"` — returns `name`, `user`, `uid`, `gitUrl`, `repoDir`,
  `publicKey`, `dockerSocket`, `runnerSocket`, `scaffolded`, `subids`, `warnings`.

**`set-credential`** (`verb_set_credential`, line ~1168) takes
`{ name, key, value }` and writes `~/.pm-creds/<key>` mode 0600 owned by the
project user. Validators: project name must match
`^[a-z0-9](?:[a-z0-9-]{0,27}[a-z0-9])?$` and must be an **existing** project user;
credential key must match `^[a-z][a-z0-9_-]{0,63}$`.

## Issues to fix

### 2.1 — No way to create a project (review §3.1)

`app/server/src/app.ts` has no `POST /api/projects`, and `grep` finds zero
`INSERT INTO projects` anywhere in the codebase. `RunnerRegistry` discovers sockets
under `/srv/pm/runners/` but never reconciles them into the DB, and every
task/comment/run route starts with `getProjectRow(name)` → 404. The header's
project `<select>` (`Header.tsx` ~line 62) has no "+ add project…" entry, so the
two-step deploy-key modal from the plan is absent.

**Fix — server:**
- `POST /api/projects` taking `{ name, gitUrl }` → `callProjectctl("create", …)`.
- Stream progress to the client. `create` can take minutes (user creation,
  rootless Docker setup, clone), so a plain request/response will look hung —
  the codebase already uses SSE for run logs; follow that pattern.
- Handle the `awaiting-key` terminal state as a **first-class success**, returning
  the public key so the UI can show it. A second `POST` with the same name and URL
  resumes; make sure that path doesn't error as "already exists".
- On `ready`, insert the `projects` row (name, git_url, repo_dir, runner socket
  path, whatever the schema holds — check the migrations) and run `rebuildIndex`
  for the new project so its `.pm/` tree lands in the cache.
- Consider whether `RunnerRegistry` should also reconcile discovered sockets into
  the DB on boot, so a project created out-of-band via SSH shows up. If you add
  it, keep `create` as the authoritative path.

**Fix — web:** add a "+ add project…" entry to the header's project select that
opens a two-step modal: (1) name + git URL → submit, show streamed progress;
(2) if `awaiting-key`, show the public key with a copy button and instructions to
add it to the repo with **write** access, plus a "Done, continue" button that
re-submits. On `ready`, refresh the project list and select the new project.

### 2.2 — Provider credentials never reach a project user (review §3.4)

`app.ts` (~line 711) calls:

```ts
callProjectctl("set-credential", { name: "_pm", credential: credName, value: body.key })
```

Three independent mismatches against `verb_set_credential`:

1. the helper reads `args["key"]`, not `args["credential"]` → `invalid_key`;
2. `_pm` fails the project-name regex → `invalid_name`; and even if it passed,
   `_require_existing` would reject it (there is no such user);
3. the key name sent is `ANTHROPIC_API_KEY`, which fails the credential-key regex
   (must be lowercase, start with a letter).

The masked row is still written to `provider_creds` and the UI reports "Connected",
so **the failure is completely silent**. `~/.pm-creds/` stays empty for every
project, the runner's credential loop (`handlers.ts` ~line 613) finds nothing, and
the agent container starts with no API key.

**Fix:**
- Correct the argument name to `key`, and use a lowercase key that satisfies
  `^[a-z][a-z0-9_-]{0,63}$` (e.g. `anthropic` / `antigravity` — pick names and make
  the runner's consumption match, see §2.3).
- There is no `_pm` project; credentials are per-project by design. **Fan out**:
  write the credential to every existing project user.
- **Re-seed on create**: the plan calls for provider credentials to be written into
  each new project user during `create`. Wire this into the `POST /api/projects`
  path from §2.1 — a project created after the key was entered must still get it.
- **Stop reporting success on failure.** If `callProjectctl` returns an error for
  any project, surface it; do not write the masked `provider_creds` row as though
  it worked. Partial success across projects needs a defined answer — pick one and
  make the UI reflect it.

Also in scope, same area: `/api/providers` advertises `authType: "oauth"` for
antigravity while the UI offers API keys only — a straight contradiction. There is
no OAuth flow implemented anywhere. **Do not build OAuth in this batch.** Make the
advertised auth type honest (API key), and leave a `TODO` naming OAuth as
unimplemented.

### 2.3 — Credentials are passed as `docker run -e KEY=value` (review §5.1)

`runner/src/handlers.ts` (~lines 619–622) passes each credential as a `-e` flag.
Process arguments are world-readable in `/proc`, so any user on the host can read
the token out of the docker CLI's argv while a run is in flight — this partially
undoes the isolation model the rest of the system works hard to maintain. The loop
is also indiscriminate: for every file in `~/.pm-creds` it exports
`<FILENAME>_API_KEY` **and** `<FILENAME>_TOKEN`, plus `ANTHROPIC_API_KEY` for three
special-cased names.

**Fix:** mount `~/.pm-creds` into the agent container **read-only** (as the plan
describes) instead of passing values on argv, and make the mapping from credential
file to what the agent reads explicit rather than a fan-out of guesses. Keep it
consistent with the key names you chose in §2.2.

### 2.4 — `/api/questions/:id/answer` is unscoped (review §5.6)

`app.ts` (~line 224) is not scoped to a project or task — any question id is
answerable by id alone. Scope it the way the neighbouring routes are scoped.
