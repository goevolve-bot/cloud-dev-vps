## Issues to fix

### 4.1 — Path traversal in the artifacts routes (review §5.2)

`app.ts` ~line 538 and ~line 558 interpolate `runNum` straight into
`join(repoPmDir, "verify-artifacts", runNum)` with no validation, while only
`filename` is checked by `isSafeFilename`. A request with `runNum` = `../../..`
reads and lists arbitrary paths reachable by the pm user. It's behind basic auth,
but the fix is trivial: validate `runNum` against `/^\d+$/`. Do this one first.

### 4.2 — Model lists are hardcoded, stale, and duplicated four times (review §4.3)

`core/src/pm/adapters/claude.ts` ~line 53, `/api/providers` (`app.ts` ~line 660),
`SettingsModal.tsx` ~line 31 and `TaskView.tsx` ~line 568 each carry their own copy
of `claude-3-5-sonnet-latest` / `claude-3-opus-latest`.

Two problems. First, the adapter's `models()` is **never called by the API**,
contrary to the plan ("choose which models populate the launch-bar dropdowns (from
each adapter's `models()`)"). Second, every listed Claude ID is two generations
behind — the current family is Claude 5, and a default run would target an outdated
model.

**Fix:** make `models()` the single source of truth, have `/api/providers` serve it,
and have both web components consume that instead of their own copies. Update the
IDs to current models.

**Before you touch the model IDs, invoke the `claude-api` skill** — it carries the
current model list and pricing, and you must not write these from memory.

### 4.3 — Contract detection keys off the project name (review §4.1)

`core/src/pm/contract.ts` ~line 60 treats the service named exactly like the project
as "the main service", and `isCompliant` is `mainServiceExists &&
mainServiceHasHealthcheck`. But the plan says only *"the main service must define a
healthcheck"* — so a repo whose compose service is `app` or `web` can never be
compliant, and its implement prompts carry the "make this repo compliant" clause
forever. Separately, `Dockerfile` presence is never checked despite being contract
item 1.

**Fix:** find a main-service rule that doesn't depend on the project name (first
non-one-shot service, or a service that exposes ports, or an explicit marker —
decide and document it), and check for a Dockerfile. Update `contract.test.ts`.

### 4.4 — Cost totals don't survive a cache rebuild (review §4.9)

`/api/costs/*` (`app.ts` ~lines 583–613) aggregate the runtime `runs` table, not
`task_runs` — which is what gets rebuilt from `.pm/`. The plan explicitly requires
the opposite, because costs are supposed to live in the run's `.pm/` file so totals
survive a rebuild. Switch the aggregation source.

### 4.5 — Duplicate artifact copies (review §4.10)

`queue.ts` ~lines 324–341 copies verify artifacts into
`PM_DATA_DIR/artifacts/<run.id>` and records `artifacts_dir`, but the serving route
reads from the repo's `.pm/verify-artifacts/<runnerRunId>/` instead. One of the two
is dead weight.

Note the plan's intent (review §6): raw logs and verify videos should live in **pm's
data dir** with retention, not in the repo working tree. B1 made `PM_DATA_DIR` real.
So prefer the data-dir copy and make the serving route read from there — then add
the retention the plan calls for, or leave a `TODO` naming it if retention policy
isn't specified anywhere.

### 4.6 — Timeline correlation is a heuristic (review §4.8)

`TaskView.tsx` ~line 708 matches a repo-side run to a runtime run by
`(phase, started_at)` string equality. Two runs of the same phase starting in the
same millisecond, or a null `started_at`, mis-associate the questions/live-log
block. B3 made pm's `runs.id` authoritative end-to-end — use it here instead of the
heuristic.

### 4.7 — Inert UI affordances (review §4.12)

All of these render and do nothing:

- Header search (`Header.tsx` ~line 85) has no handler, and there is no search API.
  Add a server-side search over the cached tasks/specs/ADRs and wire the box to it.
- The logout button does nothing. Basic auth has no clean logout; either make it do
  something honest or remove it — don't leave a dead control.
- The daemon status badge isn't clickable, and there's no `idle` state ever written.
  Start/stop currently lives buried in the settings modal.
- There's no "always on" pin in the header, which the plan calls for.
- **Verify is missing from the phase dropdown**, so it can't be re-run manually as
  the plan requires. Add it.
- The timeline shows no status-change entries.

### 4.8 — Prompt-injection note (review §5.5)

Task descriptions, comments, specs and ADRs are interpolated into prompts
(`prompts.ts` ~lines 110–118) with no delimiting, and implement runs execute with
`--dangerously-skip-permissions` and the deploy key mounted. Anything that can write
`.pm/` can steer an agent that holds push rights.

This is inherent to the design's trust model, so **don't re-architect it**. Add
clear delimiting around interpolated user content, and a comment in `prompts.ts`
stating the trust assumption explicitly so it's a documented decision rather than an
oversight.

### 4.9 — Prompt path resolution has no test (review §7)

`app/server/prompts/` is copied into the image but resolved via
`import.meta.dirname/../prompts` — correct for the built layout, but nothing proves
it. Add a test.

### 4.10 — Clear the lint backlog (review §7)

`pnpm lint` fails with ~42 errors, mostly `no-explicit-any` in `server/src/queue.ts`
and `app.ts`, plus one `prefer-const`. Lint is evidently not in anyone's loop.

Fix the violations properly — give the `any`s real types. **Do not** loosen rules in
`eslint.config.js` or scatter `eslint-disable` comments to make the count go down.
If a specific `any` is genuinely unavoidable, disable it inline with a comment
explaining why.
